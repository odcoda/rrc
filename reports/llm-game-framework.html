Architecture report

LLM Game Framework

This report sketches the framework behind the prototype: a referee-owned game engine, model adapters that only submit moves and messages, replayable transcripts, and renderers that can grow from toy games into complex board, card, negotiation, and hidden-information games.

G

Prototype Boundary

Included now

Rock Paper Scissors and Prisoner's Dilemma with hard-coded legal moves, local parsing, scoring, and model table talk.

Intentionally thin

No persistence, tournament scheduler, human seat, branching replay controls, or pluggable game package format yet.

Design direction

Keep the referee authoritative. LLMs propose actions in notation; game definitions validate, interpret, apply, and score.

System Shape

The key separation is between action generation and game authority. A player can be an LLM, human, scripted bot, or remote service, but all of them submit the same action envelope to the referee.

Move Contract

The first stable contract should be boring: every seat returns one legal move plus optional table talk. Richer games can add arguments, target IDs, bids, card references, or typed JSON, but the referee still owns interpretation.

Field Purpose Rule
MOVE Authoritative action candidate. Required. Parsed against the active game definition.
MESSAGE Side-channel speech, threat, bluff, or negotiation text. Optional. Stored as an event, rate-limited, and scoped by game visibility rules.
META Future debugging and self-reported confidence. Optional. Never used as a legal move unless a game explicitly defines it.

Core Interfaces

type PlayerId = string
type MoveNotation = string

type ActionEnvelope = {
  playerId: PlayerId
  move: MoveNotation
  message?: string
  rawResponse?: string
}

type ParseResult = {
  ok: boolean
  move?: GameMove
  errors: string[]
  normalizedNotation?: string
}

interface GameDefinition {
  id: string
  seats: SeatDefinition[]
  initialState(seed: string): GameState
  legalMoves(state: GameState, playerId: PlayerId): MoveSpec[]
  parseMove(text: string, state: GameState, playerId: PlayerId): ParseResult
  applyMove(state: GameState, move: GameMove): GameState
  score(state: GameState): Scoreboard
  visibility(state: GameState, playerId: PlayerId): PlayerView
}

interface PlayerAdapter {
  id: string
  kind: 'llm' | 'human' | 'scripted' | 'remote'
  proposeAction(view: PlayerView, contract: MoveSpec[]): Promise<ActionEnvelope>
}

Round Lifecycle

  1. Build each player's visible state, legal notation, score, clock, and recent message context.
  2. Call every player adapter required by the current phase. Simultaneous phases use the same pre-move state.
  3. Parse each response, normalize notation, and reject or repair invalid moves according to the game policy.
  4. Apply moves through the game definition and append immutable transcript events.
  5. Render the new state, compute analytics, and schedule the next phase or tournament match.

Side Channels

Side-channel messages should be first-class transcript events rather than loose prompt text. That makes table talk replayable, filterable, and visible according to the game rules.

  • Public table talk: everyone sees it before the next move. Good for RPS, Prisoner's Dilemma, diplomacy, and open negotiation.
  • Private whispers: one-to-one or coalition messages. Useful for Catan trades or hidden alliance games, but it needs audit views.
  • Out-of-band limits: cap tokens, enforce timing, and store exact prompt context so a match can be replayed or disputed.
  • Game-scoped legality: messages may negotiate, bluff, or threaten, but only game-defined move events can change state.

Human Play And Tournaments

Feature Framework hook Why it matters
Human vs LLM A human player adapter renders legal moves from PlayerView. The human UI and LLM prompt share the same legal move source.
Tournaments A scheduler creates match jobs, assigns seeds, and persists transcripts. Round robin, elimination, Swiss, ladders, and self-play use the same match runner.
Visualization Renderers subscribe to transcript events instead of reimplementing rules. Live tables, replays, heat maps, and score charts stay consistent with the referee.
Model evaluation Analytics consume normalized actions, invalid move rates, token use, and scores. Results can compare strategy, rule-following, latency, and cost.

Complex Game Path

Games like chess, poker, Catan, and Monopoly should not start as giant prompts. The framework should progressively add stronger rule modules and richer state views.

  • Chess: use SAN/UCI notation, a proven chess rules engine, clocks, repetition rules, and board renderers.
  • Poker: model hidden information with per-player views, betting phases, stack accounting, and a hand evaluator.
  • Catan: represent board topology, resources, trade offers, robber movement, and private hands as structured state.
  • Monopoly: encode turn phases, auctions, debt resolution, jail rules, property ownership, and negotiation messages.

The LLM prompt should receive a compact player view and a generated list of legal move templates. It should not be trusted to remember rules that the referee can compute.

Implementation Roadmap

  1. Extract the prototype's game definitions into a shared registry with tests for move parsing and scoring.
  2. Add a transcript event schema and local persistence so matches can be replayed after refresh.
  3. Build a human player adapter that renders legal moves from the same move specs sent to LLMs.
  4. Add tournament jobs, seed control, cost tracking, and invalid-response policies.
  5. Introduce renderer modules per game, starting with transcript-driven boards and score charts.
  6. For complex games, integrate established rules libraries before asking models to play them.
